# Student Fee Management System

A REST API built with Spring Boot to manage student records and track fee payments. It supports student registration, searching, partial payments, payment history, and fee summaries.

## Tech Stack

- Java 21
- Spring Boot 4.1.1
- Spring Data JPA / Hibernate
- PostgreSQL
- Bean Validation
- Swagger / OpenAPI
- JUnit 5 and Mockito

## Getting Started

### Prerequisites

- Java 17
- PostgreSQL

### 1. Create the database

```sql
CREATE DATABASE fee_management;
```


### 2. Configure database credentials

Set the following environment variables if you're using your own PostgreSQL instance:

```bash
export DB_USERNAME=postgres
export DB_PASSWORD=your_password
```

The default database configuration uses `localhost:5432` and the `fee_management` database.

### 3. Run the application

```bash
./mvnw spring-boot:run
```

The tables are created automatically when the application starts.

## Available APIs

| Method | Endpoint | Description |
|---|---|---|
| POST | `/api/v1/students` | Register a student |
| GET | `/api/v1/students/{id}` | Get student details |
| PUT | `/api/v1/students/{id}` | Update student details |
| DELETE | `/api/v1/students/{id}` | Deactivate a student |
| GET | `/api/v1/students?query=&page=&size=` | Search students |
| POST | `/api/v1/students/{id}/payments` | Record a fee payment |
| GET | `/api/v1/students/{id}/payments` | Get payment history |
| GET | `/api/v1/students/{id}/fee-summary` | Get fee summary |

## Business Rules

- Each student has an annual fee. Payments can be made in multiple installments.
- A payment cannot exceed the outstanding balance. Payments are also rejected if the fee is already fully paid.
- The balance and payment status are calculated from the annual fee and recorded payments.
- Payment status can be `UNPAID`, `PARTIALLY_PAID`, or `PAID`.
- Payments cannot be edited or deleted, so the payment history remains intact.
- Deleting a student marks them as `INACTIVE` instead of removing the record. Inactive students cannot make further payments.
- The annual fee can be updated, but not to an amount lower than what the student has already paid.
- Payment dates are optional and default to the current date. Future payment dates are not allowed.
- Concurrent payments are handled using a database row lock to prevent overpayments.

## Sample Requests

### 1. Register a student

```bash
curl -X POST http://localhost:8080/api/v1/students \
  -H "Content-Type: application/json" \
  -d '{
    "admissionNumber": "ADM001",
    "name": "Rahul Sharma",
    "className": "8-A",
    "annualFee": 50000
  }'
```

### 2. Record a partial payment

```bash
curl -X POST http://localhost:8080/api/v1/students/1/payments \
  -H "Content-Type: application/json" \
  -d '{
    "amount": 20000,
    "paymentMethod": "UPI"
  }'
```

The outstanding balance will be ₹30,000, and the status will be `PARTIALLY_PAID`.

### 3. Try to overpay (rejected)

```bash
   curl -X POST http://localhost:8080/api/v1/students/1/payments \
     -H "Content-Type: application/json" \
     -d '{"amount": 40000, "paymentMethod": "CASH"}'
```

Returns `400 Bad Request`: the payment exceeds the outstanding balance of ₹30,000.

### 4. Get the fee summary

```bash
curl http://localhost:8080/api/v1/students/1/fee-summary
```

### 5. Get payment history

```bash
curl http://localhost:8080/api/v1/students/1/payments
```

### 6. Search students

```bash
curl "http://localhost:8080/api/v1/students?query=rahul&page=0&size=10"
```

## Error Handling

The API returns consistent error responses for validation failures, business rule violations, and unexpected errors.

| Status Code | Description |
|---|---|
| `400 Bad Request` | Invalid input or business rule violation |
| `404 Not Found` | Student not found |
| `409 Conflict` | Duplicate admission number |
| `500 Internal Server Error` | Unexpected server error |

## Running Tests

Run the service-layer unit tests with:

```bash
./mvnw test
```

The tests use JUnit 5 and Mockito to test service logic without requiring a running database.

## Assumptions

- The system is used by school staff to record payments received through methods such as cash or UPI. It does not process payments through a payment gateway.
- The application is designed for a single school with one annual fee per student.
- Admission numbers are unique and assigned by the school.
- Receipt numbers are generated by the system.
- Student search supports partial, case-insensitive name matching and exact admission number matching. Results are sorted by name.


## Future Improvements

- **Authentication:** Left out because of the time limit; the API assumes a trusted internal network. The next step would be Spring Security with JWT and an admin role (I've implemented this in a previous project).
- **Fee management:** Support multiple academic years and predefined fee installments.
- **Refunds:** Add a way to handle refunds and payment corrections without changing existing payment records.
- **Database migrations:** Use Flyway to manage database schema changes instead of relying on Hibernate.
- **Testing:** Add integration tests for database operations and concurrent payments.
